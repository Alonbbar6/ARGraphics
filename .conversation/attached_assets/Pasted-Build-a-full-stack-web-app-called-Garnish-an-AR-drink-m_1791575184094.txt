Build a full-stack web app called "Garnish": an AR drink menu platform for independent cocktail bars. Bar owners use this web app to upload photos of their drinks, run them through an AI cleanup step and Meshy's image-to-3D API, and publish the 3D models and prices to a native iOS AR app. The iOS app (already being built separately in Swift with ARKit image tracking) reads everything from this app's API. This web app is the backend and admin dashboard for that iOS app.

TARGET USER
Independent bar owners, 30 to 45, hands-on, not technical, skeptical of tech after bad experiences with agencies and QR menus. They use the dashboard on a phone behind the bar mid-shift and on a laptop late at night. Every core flow must be fast, one-handed on mobile, and use bar language (drinks, menu, prices, table cards), not tech language (models, assets, pipelines). Never show the words "Meshy", "GLB", or "USDZ" to owners in the UI.

TECH STACK
- Frontend: React + Vite + TypeScript, Tailwind CSS, DaisyUI, Framer Motion, Heroicons
- Backend: Node + Express + TypeScript
- Database: Replit PostgreSQL with Drizzle ORM
- File storage: Replit Object Storage for drink photos, cleaned images, 3D model files, and table card images
- Auth: email + password with secure sessions (bcrypt hashing); each owner account belongs to one bar
- Secrets (use Replit Secrets, never hardcode): MESHY_API_KEY, SESSION_SECRET, IOS_API_KEY

BUILD IN THIS ORDER, and confirm each phase works before moving to the next:
Phase 1: database schema, auth, dashboard shell
Phase 2: drinks and price management
Phase 3: photo upload, AI cleanup, Meshy 3D generation
Phase 4: 3D preview and publish

PHASE 3: PHOTO TO 3D PIPELINE (the core feature)
Step 1, Upload: drag-and-drop dropzone on desktop, camera capture as the default on mobile (input accept="image/*" capture="environment"). Accept JPG, PNG, HEIC. Convert HEIC to JPG server-side. Show tips: "One drink, good light, plain background."
Step 2, AI cleanup ("Polishing your photo"): on the server, crop to the drink, remove the background, and output a clean PNG with transparency, since Meshy produces much better models from a single isolated object. Use the @imgly/background-removal-node package (runs locally, no extra API key). Store both the original and the cleaned image. Show the owner a before/after so they can approve or re-shoot.
Step 3, Generate ("Building your drink"): send the cleaned image to Meshy's Image to 3D API. Read Meshy's current API docs at https://docs.meshy.ai before implementing and use the current endpoints. The flow is: POST to create an image-to-3d task with the image (public URL or base64 data URI), with texturing enabled and a moderate polycount suitable for mobile AR; store the returned task id; poll the task status every 5 seconds from a server-side background job (not from the browser); when it succeeds, download the GLB, USDZ, and thumbnail files immediately and save them to Replit Object Storage, because Meshy's download URLs expire. Never expose MESHY_API_KEY to the frontend.
Step 4, Progress UI: show live status (Uploading, Polishing, Building, Finishing, Ready) with a custom animation of a glass outline filling from deep plum to amber as progress advances. Use polling from the frontend to our own backend every 3 seconds. If generation fails, show a friendly message ("That photo didn't work. Try better light or a plainer background.") with a Retry button, and save the error.
Step 5, Review: when ready, move the drink to "Needs review" and open the preview.

PHASE 5: TABLE CARDS AND THE iOS API
Table Cards page:
- Upload the card artwork, coaster illustration, or bar logo that the iOS app will use as the ARKit reference image. Set its printed width in centimeters (store in meters)
- Warn if the image is low resolution (under 1000px on the long side) or low contrast, since ARKit needs detailed, high-contrast images to track
- Download a print-ready PDF of the card at the correct physical size

Public read-only API for the iOS app, authenticated with an x-api-key header matching IOS_API_KEY:
- GET /api/v1/bars/:slug/menu-version returns { version } so the app can cheaply check for updates
- GET /api/v1/bars/:slug/menu returns the bar name, logo, and all published, available drinks sorted by sort_order: id, name, description, price (formatted and cents), category, thumbnail_url, model_usdz_url, model_glb_url, updated_at
- GET /api/v1/bars/:slug/table-cards returns active cards: id, name, reference_image_url, physical_width_meters
- POST /api/v1/bars/:slug/events accepts { drink_id, event_type } to log AR views and taps
- Add CORS, rate limiting, input validation (zod), and proper error codes
- Create an "API" page in Settings showing the bar slug and example requests so I can wire up the Swift app
